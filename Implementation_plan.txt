TRACE — Module 2 Source of Truth
KPI Signal & Materiality Engine

Purpose of this document: This file is the authoritative implementation specification for Module 2. Coding assistants must follow it when implementing or modifying Module 2. Module 2 consumes the governed KPI layer created by Module 1 and determines whether a KPI movement is meaningful, abnormal, material, and worth investigating.

Critical rule: Module 2 must not use an LLM to determine whether a numerical KPI movement is significant. Quantitative signal detection must use deterministic logic, statistics, business rules, and/or traditional ML.

1. Module 2 Objective

Module 2 answers:

"Did something meaningful actually change, or is this normal business noise?"

A dashboard showing:

Revenue ↓ 8%

does not automatically mean there is a business problem.

The movement could be:

normal weekly/monthly variation
seasonal
caused by a holiday
within historical volatility
statistically insignificant
statistically significant but financially immaterial
financially material but statistically noisy
a genuine anomaly requiring investigation

Module 2 must distinguish these cases.

7. Period-over-Period Analysis

Calculate:

Absolute change
Absolute Change =
Current KPI - Previous KPI

Example:

₹9.1M - ₹10.1M
= -₹1.0M
Percentage change
Change % =
(Current - Previous) / Previous × 100

Example:

(9.1 - 10.1) / 10.1 × 100
= -9.9%
8. Baseline Calculation

Do not rely only on the immediately previous period.

Module 2 must construct a historical baseline.

For monthly KPIs, initially use:

Trailing 6 months

or:

Trailing 12 months

when sufficient history exists.

Calculate:

mean
median
standard deviation
MAD
percentiles

Use robust statistics where appropriate.

9. Robust Baseline

Business data often contains outliers.

Therefore calculate both:

mean

and:

median

and use:

MAD = Median Absolute Deviation

as a robust volatility measure.

This prevents one extreme historical event from making the baseline unreliable.

10. Statistical Significance

Module 2 should determine whether the current observation is unusual relative to historical behaviour.

Initial implementation can use:

Z-score
z = (current - historical_mean) / historical_std

Interpretation:

|z| < 1
Normal

1 ≤ |z| < 2
Potential movement

2 ≤ |z| < 3
Significant movement

|z| ≥ 3
Highly unusual

These thresholds must be configurable.

11. Robust Z-score

When the history contains outliers, use:

robust_z =
0.6745 × (current - median) / MAD

If MAD is zero or history is too short, fall back to another method.

Do not crash or produce infinite values.

12. Minimum Historical Coverage

Signal confidence depends on historical coverage.

Recommended:

< 3 periods
Very low confidence

3–5 periods
Low confidence

6–11 periods
Moderate confidence

≥ 12 periods
Good historical confidence

This is especially important for newly launched KPIs.

13. Sparse-History Scenario

One sparse-history or newly launched KPI scenario.

Module 2 must detect this.

Example:

History:
May   ₹100K
June  ₹120K
July  ₹110K
August ₹160K

Do not claim:

"Revenue is definitely anomalous."

Instead:

  "status": "watch",
  "confidence": 0.42,
  "reason": "Insufficient historical baseline"
}
14. Seasonality Detection

A movement can be normal because of seasonality.

Example:

December Revenue ↓

might be normal for a particular business.

Therefore Module 2 must compare the current period with an appropriate seasonal baseline when enough history exists.

For monthly data:

August 2026

should ideally be compared against:

August 2025

as well as:

July 2026

when sufficient history exists.

15. Seasonality-Aware Comparison

Produce both:

MoM change
YoY change

Example:

MoM: -9.9%
YoY: +4.2%

Interpretation:

Revenue fell from July,
but remains above last year's August.

→ likely seasonal/normal rather than an immediate anomaly.

The system should not automatically call it a problem.

16. Business Materiality

Statistical significance alone is insufficient.

Example:

Revenue = ₹10,000,000
Movement = -0.5%

Statistically significant perhaps, but:

Business impact = ₹50,000

which might not justify investigation.

Conversely:

Revenue = ₹100,000,000
Movement = -3%

could represent:

₹3M loss

and be highly material.

Therefore Module 2 must calculate business materiality independently.

17. Materiality Threshold

Each KPI should have a configurable threshold.

Example:

Revenue:
absolute threshold = ₹500,000
relative threshold = 3%

Orders:
absolute threshold = 500
relative threshold = 5%

AOV:
relative threshold = 3%

Conversion:
relative threshold = 2 percentage points

These values should live in KPI definitions/configuration, not inside the algorithm as hardcoded constants.

18. Materiality Classification

Use:

LOW
MEDIUM
HIGH

Example:

Revenue loss:
< ₹250K → LOW
₹250K–₹1M → MEDIUM
> ₹1M → HIGH

These are illustrative and should be configurable.

19. Statistical Significance vs Business Materiality

Module 2 must keep these dimensions separate.

Example:

                  Statistical
                  Significance

20. Volatility

Calculate historical volatility.

Use:

standard deviation

and preferably:

coefficient of variation

where appropriate:

CV = standard deviation / mean

This allows the system to distinguish:

Revenue normally fluctuates ±2%

from:

Revenue normally fluctuates ±15%

A 5% movement means very different things in these two cases.

21. Signal Strength

Create a normalized signal score:

0 → no meaningful signal

1 → extremely strong signal

Signal strength can combine:

statistical deviation
+
business materiality
+
historical confidence
+
data quality
+
seasonality adjustment

Do not use an LLM to calculate it.

22. Recommended Signal Formula

Use a transparent weighted formula initially.

Example:

signalStrength =
    0.35 × statisticalScore
  + 0.30 × materialityScore
  + 0.15 × historicalConfidence
  + 0.10 × dataQualityScore
  + 0.10 × seasonalityAdjustedScore

Weights must be configurable.

Do not hide the calculation.

The API should expose the component scores.

23. Signal Priority

Convert signal strength into:

LOW
MEDIUM
HIGH
CRITICAL

Example:

0.00–0.25 → LOW
0.25–0.50 → MEDIUM
0.50–0.75 → HIGH
0.75–1.00 → CRITICAL

These thresholds should be configurable.

24. Signal Status

URGENT

Example:

No meaningful movement.

Watch:
Potential movement, insufficient evidence/history.

Very large, high-confidence, high-impact movement.

The most important rule for Module 2 is:

Do not confuse a KPI movement with a KPI signal.

A KPI movement is simply:

Revenue ↓ 8%

A KPI signal is:

Revenue ↓ 8%
+ outside historical volatility
+ financially material
+ seasonally adjusted
+ healthy data
+ sufficient history
= HIGH-CONFIDENCE INVESTIGATION SIGNAL

That distinction is what turns a normal BI dashboard into an actual KPI intelligence engine.

10. Contribution Analysis

This is one of the most important parts of Module 3.

The system should determine:

11. Revenue Decomposition

Revenue has a fundamental relationship:

Revenue = Orders × AOV

Therefore:

Revenue change
    ↓
Orders contribution
    +
AOV contribution

Example:

Previous:
Orders = 100,000
AOV = ₹100
Revenue = ₹10M

Current:
Orders = 96,000
AOV = ₹95
Revenue = ₹9.12M

The system should decompose the change into:

Orders effect
+
AOV effect
+
interaction/residual
12. Shapley-Style Decomposition

For multi-factor decomposition, implement a transparent contribution method.

For two drivers:

Revenue = Orders × AOV

Use a Shapley-style decomposition.

Conceptually:

Orders contribution
=
average of:
1. changing Orders first
2. changing Orders after AOV

and:

AOV contribution
=
average of:
1. changing AOV first
2. changing AOV after Orders

This prevents arbitrary ordering from determining the result.

For the prototype, exact Shapley decomposition is preferred when the number of factors is small.

This is more plausible than:

August 1–10

Stockouts stable

14. LLM Role

✓ synthesize verified findings
✓ generate natural-language explanations
✓ adapt narrative to persona
✓ summarize evidence
✓ explain uncertainty
✓ phrase recommendations
✓ identify decision context

The LLM cannot:

❌ calculate KPI values
❌ invent contribution percentages
❌ override evidence confidence
❌ invent evidence
❌ invent sources
❌ make unsupported causal claims
❌ fabricate expected financial impact
15. Grounded Story Generation

The LLM prompt should explicitly say:

Use only the supplied analytical context.

Do not introduce new numerical values.

Do not invent evidence.

Do not state correlation as causation.

If evidence is contradictory, explicitly state that.

If confidence is low, recommend further investigation
rather than presenting a definitive explanation.

The fundamental design rule for Module 5

Modules 1–4 establish what the system is justified in believing. Module 5 decides how to communicate that belief and what action to propose.

So the LLM sits primarily here:

Verified analytical context
          ↓
        LLM
          ↓
Natural-language story
+
persona adaptation
+
action phrasing

—not here:

Raw database
    ↓
   LLM
    ↓
"Revenue fell because..."

That distinction should remain enforced throughout the implementation.


TRACE — Module 6 Source of Truth
Security, Governance, Observability, Evaluation & Learning Operations

Purpose: Module 6 is the trust, control, evaluation, and operational layer around Modules 1–5.

It ensures that TRACE does not merely produce an intelligent-looking answer, but can demonstrate:

Who was allowed to see what → which data was used → which analytical methods ran → which model was called → what the system concluded → how confident it was → what action was recommended → what the human decided → what happened afterward.

This module is particularly important because the BusinessIntelligence.ai challenge explicitly requires realistic security, cost, latency, scalability, auditability, model/data drift, feedback capture, continuous evaluation, and LLM economics.

1. Module 6 Objective

Module 6 answers:

1. WHO can access this information?
2. WHAT data was used?
3. WHY was this evidence accessible?
4. WHICH analytical method produced each result?
5. WHICH model/prompt generated the narrative?
6. HOW much did the analysis cost?
7. HOW long did it take?
8. HOW reliable is the system?
9. DID the human agree or override it?
10. IS the system getting better or worse over time?

25. LLM Cost Calculation

Do not hard-code cost into business logic.

Create:

src/server/observability/cost.ts

Configuration:

MODEL_PRICING = {
  "model-a": {
    inputPerMillion: ...,
    outputPerMillion: ...
  }
}

Then:

cost =
(inputTokens / 1,000,000 × inputPrice)
+
(outputTokens / 1,000,000 × outputPrice)

This allows model changes without rewriting the system.

The key idea

Modules 1–5 make TRACE intelligent.

Module 6 makes TRACE trustworthy and demonstrable.

For the Accenture challenge, that distinction is important. A system that says "AI thinks revenue fell because of stockouts" is relatively easy to build. A system that can additionally demonstrate:

"This user was authorized to see these records; these exact sources produced the evidence; these deterministic calculations produced the numbers; this model generated the narrative; it cost X and took Y ms; the evidence confidence was Z; the user challenged the conclusion; and here is whether the recommendation was ultimately accepted and effective."

is much closer to the production-grade KPI intelligence-to-action engine described in the problem statement.
